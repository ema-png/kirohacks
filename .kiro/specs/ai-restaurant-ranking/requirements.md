# Requirements Document

## Introduction

The AI-Powered Restaurant Ranking feature enables groups of 1–8 people to find and rank nearby restaurants that collectively satisfy everyone's dietary restrictions, flavor preferences, budget constraints, and dining style preferences. The user provides a location, selects a vibe and cuisine, and configures per-person preferences. The system fetches live restaurant data from the Yelp Fusion API, sends the results to OpenAI GPT-4o-mini for intelligent group-aware ranking, and displays a ranked list of up to 8 restaurants with per-restaurant reasoning, group satisfaction scores, and direct Yelp links.

---

## Glossary

- **RankingAPI**: The Express.js backend service exposing `POST /api/rank` on port 3001.
- **YelpClient**: The module within RankingAPI responsible for querying the Yelp Fusion API.
- **AIRanker**: The module within RankingAPI responsible for sending restaurant data and group preferences to OpenAI GPT-4o-mini and parsing the response.
- **RankRestaurantsClient**: The frontend utility (`src/api/rankRestaurants.js`) that calls `POST /api/rank` and returns structured results to the UI.
- **OnboardingFlow**: The multi-step frontend wizard (Location → Vibe → Group → Results) that collects user inputs and renders results.
- **StepResults**: The frontend component that invokes RankRestaurantsClient, displays ranked restaurant cards, and provides sort controls.
- **LoadingScreen**: The frontend component that displays animated progress steps while the ranking request is in flight.
- **Person**: A group member with optional name, dietary restrictions, flavor preferences, avoided ingredients, and a per-meal budget.
- **HardDietaryRestriction**: A dietary restriction that must be fully accommodated for a restaurant to be eligible. The hard restrictions are: Vegan, Vegetarian, Halal, Nut-Free, and Gluten-Free.
- **SoftPreference**: A preference (flavor craving, avoided ingredient, budget) that influences ranking score but does not disqualify a restaurant.
- **Vibe**: A dining style descriptor (e.g., Casual, Fancy, Sit-Down, Fast Casual, Drive-Thru, Takeout/Delivery, Outdoor Seating, Bar/Drinks Too).
- **Cuisine**: A food category preference (e.g., Mexican, Italian, Japanese) used to filter Yelp search categories.
- **RankedRestaurant**: A restaurant object returned by the RankingAPI, enriched with AI-generated score, reasoning, group satisfaction count, and dietary pass/fail flags.
- **GroupMatchBar**: The visual progress bar on each restaurant card showing what fraction of the group is satisfied.
- **AISummary**: A 2-sentence natural-language explanation of why the top-ranked restaurant is the best pick for the group.
- **GroupInsight**: A single sentence describing the group's key constraints or preferences, generated by the AIRanker.

## Requirements

### Requirement 1: Group Preference Collection

**User Story:** As a group organizer, I want to enter preferences for each person in my group, so that the AI can find restaurants that work for everyone.

#### Acceptance Criteria

1. THE OnboardingFlow SHALL collect a location string (city, neighborhood, or address) before proceeding to vibe and group steps.
2. THE OnboardingFlow SHALL allow the user to select one or more Vibe options from the predefined list: Casual, Fancy, Sit-Down, Fast Casual, Drive-Thru, Takeout/Delivery, Outdoor Seating, Bar/Drinks Too.
3. THE OnboardingFlow SHALL allow the user to select zero or more Cuisine options from the predefined list of 21 cuisine types.
4. WHERE the user wants a cuisine not in the predefined list, THE OnboardingFlow SHALL accept a free-text "Other cuisine" input.
5. THE OnboardingFlow SHALL support between 1 and 8 Person entries in a single session.
6. FOR EACH Person, THE OnboardingFlow SHALL allow selection of zero or more dietary restrictions from: Vegan, Vegetarian, Keto, Gluten-Free, Halal, Dairy-Free, Nut-Free.
7. FOR EACH Person, THE OnboardingFlow SHALL allow selection of zero or more flavor preferences from: Savory, Spicy, Sweet, Salty, Comfort Food, Light, Umami, Smoky.
8. FOR EACH Person, THE OnboardingFlow SHALL allow selection of zero or more avoided ingredients from: Mushrooms, Onions, Seafood, Red Meat, Pork, Eggs, Soy, Gluten.
9. FOR EACH Person, THE OnboardingFlow SHALL allow a single per-meal budget selection from the predefined range ($5 to $100+).
10. WHERE a user wants to specify a dietary restriction, flavor, or avoidance not in the predefined list, THE OnboardingFlow SHALL accept a free-text "Other" input for each category.
11. THE OnboardingFlow SHALL display a 4-step progress indicator (Location, Vibe, Group, Results) that reflects the current step.

### Requirement 2: Yelp Restaurant Fetching

**User Story:** As a user, I want the system to find real, currently open restaurants near my location, so that the results are actionable.

#### Acceptance Criteria

1. WHEN a ranking request is received, THE YelpClient SHALL query the Yelp Fusion API using the provided location string.
2. THE YelpClient SHALL map selected Vibe options to Yelp category aliases (e.g., "fancy" → `newamerican,french,italian`; "bar" → `bars`).
3. THE YelpClient SHALL map selected Cuisine options to Yelp category aliases (e.g., "indian" → `indpak`; "american" → `newamerican,tradamerican`).
4. WHERE multiple cuisines are selected, THE YelpClient SHALL issue one Yelp search per cuisine and merge results, deduplicating by Yelp business ID, so that each cuisine type is fairly represented.
5. WHERE a free-text "Other cuisine" is provided, THE YelpClient SHALL issue a Yelp term-based search using that text.
6. THE YelpClient SHALL request only currently open businesses by default (`open_now=true`).
7. THE YelpClient SHALL return up to 20 restaurants per search, sorted by `best_match`.
8. FOR EACH restaurant returned, THE YelpClient SHALL normalize the data into a RankedRestaurant candidate containing: id, name, cuisine label, address, distance in miles, Yelp star rating, review count, price tier ($–$$$$), Yelp URL, coordinates, and open status.
9. THE YelpClient SHALL assign a cuisine emoji to each restaurant based on its Yelp category aliases and name.
10. IF the Yelp API returns an error, THEN THE RankingAPI SHALL return HTTP 500 with a descriptive error message.
11. IF no restaurants are found for the given location and filters, THEN THE RankingAPI SHALL return HTTP 404 with the message `No restaurants found near "{location}"`.

### Requirement 3: AI-Powered Group Ranking

**User Story:** As a group, I want the AI to rank restaurants based on everyone's preferences simultaneously, so that we get a result that works for the whole group rather than just one person.

#### Acceptance Criteria

1. WHEN restaurant candidates are available, THE AIRanker SHALL send the full restaurant list and all group member preferences to OpenAI GPT-4o-mini using a structured prompt.
2. THE AIRanker SHALL instruct the model to return results as a JSON object with the fields: `rankedIds`, `scores`, `passesHardDiet`, `passesBudget`, `satisfiedCounts`, `reasoning`, `aiSummary`, and `groupInsight`.
3. THE AIRanker SHALL use `response_format: { type: "json_object" }` and `temperature: 0.3` to ensure deterministic, parseable output.
4. THE AIRanker SHALL include each Person's name, dietary restrictions, flavor cravings, avoided ingredients, and budget in the prompt.
5. THE AIRanker SHALL include each restaurant's name, cuisine, price tier, Yelp rating, distance, and address in the prompt.
6. THE AIRanker SHALL instruct the model to return up to 8 ranked restaurant indices.
7. THE AIRanker SHALL enforce the HardDietaryRestriction rule: IF any Person has a HardDietaryRestriction (Vegan, Vegetarian, Halal, Nut-Free, Gluten-Free), THEN the model SHALL mark restaurants that cannot accommodate it as `passesHardDiet: false`.
8. THE RankingAPI SHALL exclude any restaurant where `passesHardDiet` is `false` from the final ranked list returned to the client.
9. THE RankingAPI SHALL exclude any restaurant where `satisfiedCount` is 0 from the final ranked list returned to the client.
10. THE AIRanker SHALL map numeric restaurant indices in the AI response back to real Yelp business IDs before returning results.
11. IF the OpenAI API returns an error or unparseable JSON, THEN THE RankingAPI SHALL return HTTP 500 with a descriptive error message.

### Requirement 4: Ranking API Contract

**User Story:** As a frontend developer, I want a well-defined API contract for the ranking endpoint, so that the frontend can reliably consume results.

#### Acceptance Criteria

1. THE RankingAPI SHALL expose `POST /api/rank` accepting a JSON body with fields: `people` (array), `vibe` (array of strings), `cuisine` (array of strings), `otherCuisine` (string), `openNow` (boolean), and `location` (string).
2. IF the `people` array is empty, THEN THE RankingAPI SHALL return HTTP 400 with `{ "error": "No people provided" }`.
3. IF the `location` field is empty or whitespace, THEN THE RankingAPI SHALL return HTTP 400 with `{ "error": "No location provided" }`.
4. WHEN ranking succeeds, THE RankingAPI SHALL return HTTP 200 with a JSON body containing: `ranked` (array of RankedRestaurant), `aiSummary` (string or null), `groupInsight` (string or null), and `usedFallback` (boolean, always `false` on success).
5. FOR EACH RankedRestaurant in the response, THE RankingAPI SHALL include: `id`, `name`, `emoji`, `cuisine`, `address`, `distance`, `rating`, `reviews`, `price`, `priceNum`, `yelpUrl`, `lat`, `lng`, `isOpen`, `score` (0–100), `passesHardDiet` (boolean), `passesBudget` (boolean), `satisfiedCount` (integer), `totalPeople` (integer), and `reasoning` (string or null).
6. THE RankingAPI SHALL expose `GET /health` returning `{ "status": "ok" }` for liveness checks.

---

### Requirement 5: Frontend API Client

**User Story:** As a frontend component, I want a resilient API client that handles errors gracefully, so that the UI never crashes when the backend is unavailable.

#### Acceptance Criteria

1. THE RankRestaurantsClient SHALL call `POST /api/rank` with a 60-second timeout using `AbortSignal.timeout(60_000)`.
2. THE RankRestaurantsClient SHALL read the backend base URL from the `VITE_API_URL` environment variable, defaulting to `http://localhost:3001`.
3. IF the API call succeeds, THE RankRestaurantsClient SHALL return the response body augmented with `usedFallback: false` and `error: null`.
4. IF the API call fails for any reason (network error, timeout, non-2xx status), THEN THE RankRestaurantsClient SHALL return `{ ranked: [], aiSummary: null, groupInsight: null, usedFallback: true, error: <message> }` without throwing.
5. THE RankRestaurantsClient SHALL parse non-2xx responses as JSON to extract the `error` field before constructing the error message.

### Requirement 6: Loading Experience

**User Story:** As a user, I want to see meaningful progress feedback while the AI is working, so that I understand what is happening and feel confident the app is running.

#### Acceptance Criteria

1. WHEN the ranking request is in flight, THE LoadingScreen SHALL display a sequence of 6 animated progress steps: "Finding restaurants nearby…", "Applying vibe filters…", "Checking dietary restrictions…", "Balancing budgets…", "Matching flavor profiles…", "Ranking results for your group…".
2. THE LoadingScreen SHALL advance through steps at approximately 380ms intervals.
3. THE LoadingScreen SHALL display a summary card showing each Person's name, avatar, dietary tags, and budget alongside a natural-language brief of the group's preferences.
4. THE LoadingScreen SHALL display a pulsing robot emoji (🤖) icon with a ping animation while loading.
5. WHEN all steps are complete, THE LoadingScreen SHALL transition to StepResults after a 500ms delay.

---

### Requirement 7: Results Display

**User Story:** As a user, I want to see ranked restaurant results with clear explanations of why each restaurant was chosen, so that I can make an informed decision for my group.

#### Acceptance Criteria

1. WHEN ranked results are available, THE StepResults SHALL display up to 8 RankedRestaurant cards in ranked order by default.
2. THE StepResults SHALL label the first-ranked restaurant with a "⭐ BEST MATCH FOR YOUR GROUP" banner.
3. FOR EACH restaurant card, THE StepResults SHALL display: rank number, cuisine emoji, restaurant name, cuisine label, Yelp star rating, distance in miles, price tier, address, open/closed status, GroupMatchBar, AI reasoning text, cuisine tags, dietary tags, flavor tags, and a "View on Yelp" link.
4. THE GroupMatchBar SHALL display a progress bar representing `satisfiedCount / totalPeople` as a percentage, with the label "{satisfiedCount}/{totalPeople} people satisfied".
5. THE StepResults SHALL provide three sort options: "⭐ Best match" (default, AI rank order), "📍 Nearest" (ascending distance), "★ Top rated" (descending Yelp rating).
6. WHEN a sort option is selected, THE StepResults SHALL re-sort the displayed list without re-fetching from the API.
7. THE StepResults SHALL display a collapsible "Filters used for this search" summary card showing location, vibe tags, cuisine tags, and per-person preference details.
8. THE StepResults SHALL display a "Start over" button that resets the OnboardingFlow to the initial state.
9. IF no ranked results are returned, THEN THE StepResults SHALL display an error state with the message from the API response and a "Try again" button.
10. WHILE the ranking request is in flight, THE StepResults SHALL display a spinner and the message "Finding restaurants for your group…".

---

### Requirement 8: Hard Dietary Restriction Enforcement

**User Story:** As a group member with a hard dietary restriction, I want to be certain that no restaurant violating my restriction appears in the results, so that I never have to worry about being excluded.

#### Acceptance Criteria

1. THE RankingAPI SHALL treat the following dietary restrictions as hard constraints: Vegan, Vegetarian, Halal, Nut-Free, Gluten-Free.
2. WHEN any Person in the group has one or more HardDietaryRestrictions, THE AIRanker SHALL explicitly instruct the model to skip any restaurant that cannot accommodate those restrictions.
3. THE RankingAPI SHALL apply a post-processing filter: IF a restaurant's `passesHardDiet` flag is `false`, THEN THE RankingAPI SHALL remove it from the `ranked` array before responding.
4. THE RankingAPI SHALL apply a post-processing filter: IF a restaurant's `satisfiedCount` is 0, THEN THE RankingAPI SHALL remove it from the `ranked` array before responding.
5. THE RankingAPI SHALL not apply hard enforcement to soft preferences (Keto, Dairy-Free, flavor cravings, avoided ingredients, budget) — these influence score only.

---

### Requirement 9: Per-Restaurant AI Reasoning

**User Story:** As a user, I want to read a short explanation for each restaurant, so that I understand why the AI ranked it where it did.

#### Acceptance Criteria

1. THE AIRanker SHALL request a one-sentence `reasoning` string for each ranked restaurant from the model.
2. THE AIRanker SHALL request a 2-sentence `aiSummary` explaining why the top-ranked restaurant is the best pick for the group.
3. THE AIRanker SHALL request a one-sentence `groupInsight` describing the group's key constraints or preferences.
4. THE RankingAPI SHALL pass `aiSummary` and `groupInsight` through to the API response at the top level.
5. FOR EACH RankedRestaurant, THE StepResults SHALL display the `reasoning` string prefixed with "✦" when it is non-null.

---

### Requirement 10: Score-Based Ranking

**User Story:** As a user, I want restaurants ranked by how well they match the whole group's preferences, so that the best overall option appears first.

#### Acceptance Criteria

1. THE AIRanker SHALL request a numeric `score` between 0 and 100 for each ranked restaurant, reflecting overall group fit.
2. THE RankingAPI SHALL include the `score` field on each RankedRestaurant in the response.
3. THE StepResults SHALL use the AI-provided rank order (position in `rankedIds`) as the default sort, not the numeric score directly.
4. THE AIRanker SHALL instruct the model to use dietary needs, flavor cravings, avoided ingredients, budget, and cuisine preferences as the primary ranking signals.
5. THE AIRanker SHALL instruct the model that a Person with no preferences is automatically satisfied by any restaurant.

---

### Requirement 11: Configuration and Environment

**User Story:** As a developer, I want the service to be configurable via environment variables, so that API keys and ports can be changed without modifying code.

#### Acceptance Criteria

1. THE RankingAPI SHALL read the Yelp Fusion API key from the `YELP_API_KEY` environment variable.
2. THE RankingAPI SHALL read the OpenAI API key from the `OPENAI_API_KEY` environment variable.
3. THE RankingAPI SHALL read the server port from the `PORT` environment variable, defaulting to `3001`.
4. IF `YELP_API_KEY` is not set, THEN THE YelpClient SHALL throw an error with the message `"YELP_API_KEY not set in .env"`.
5. THE RankRestaurantsClient SHALL read the backend base URL from the `VITE_API_URL` environment variable, defaulting to `http://localhost:3001`.
6. IF port `3001` (or the configured port) is already in use, THEN THE RankingAPI SHALL log a descriptive error message and exit with a non-zero status code.
